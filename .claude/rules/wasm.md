# WebAssembly engine rules

- Build only with `wasm/build.sh` (clang 22, `--target=wasm32 -Os -nostdlib`, no emscripten, no libc, no imports). It first regenerates `dispatch.h` from the `HOT` list in `tools/gen-dispatch.mjs`; both outputs are committed and two builds must be byte-identical (`md5sum`).
- Commit `42mars.wasm` together with the C change it was built from.
- The same `mars.c` builds natively for `tools/bench-native.mjs` (`bench-native.c`, static arena). Keep it building: the native profile (`perf stat`, `perf record`) is the main tool for finding where time goes.
- Instruction code lives in `exec_ins()`. `step()` switches on the 14-bit instruction word: the 32 hottest words call `exec_ins()` with a constant word (specialized copies), the rest run it generically. Loops: `execute` (any number of warriors) and `execute2` (exactly two, a loop over pairs of turns with one queue head for both warriors and the two tails in locals), instantiated as `execute2_8000` (core 8000, 8000 processes as constants) and `execute2_any`. A semantics change in `exec_ins()` reaches all of them; the test "every specialized instruction word agrees with mars.js" covers each specialized word in each loop.
- To re-rank the hot words for a new instruction mix: `node tools/bench-native.mjs --input <file> --early-tie --count <counts>` per mix (inputs from `--native-input` of `tools/tournament.mjs` and `tools/bench-pairs.mjs`), then `node tools/gen-dispatch.mjs --rank <count files>` prints a new `HOT` list. Changes to the set of cases move V8's code by a few percent either way, also where the native build does not move (issue #10): measure in wasm, not natively.
- Two warriors with `maxCycles` up to 80000 run on linear queues without a mask (`config()` in `mars.c`): a queue starts at index 0 or 1 and each tail stays at most `2 + 2 * (maxCycles + 1)` because a round runs at most `max(2 * maxCycles, 1)` instructions and a turn pushes at most two entries. Anything that lets a round run longer or a turn push more breaks that bound; the test "full queues at the linear queue limit and above" fills the queues. `execute2` relies on both heads being equal whenever warrior 0 is to move: `start_round()` starts warrior 0's queue at index 1 when warrior 1 moves first, and every path out of `execute2` has to leave the heads that way.
- `runMatch({ firstRound })` plays a block of a match with empty p-space; blocks equal the whole match only when no warrior's code has `LDP` (`tools/tournament.mjs` checks that; it plays every other pairing as blocks of 8 rounds). Anything new that carries state from one round to the next breaks the split.
- `runMatch` early ties (process-count proof, no-killer scan, both at most 4096 instructions apart) must be exact: same scores and round results as without them. Any new early exit needs that proof written in the semantics doc, section 3.7. Before building one, measure its ceiling with `tools/tie-ceiling.mjs` (closed-loop oracle per tie round, #27); `lib/tools/tie-ceiling.c` builds `mars.c` with `-DTRACE_TIES`, which must stay out of the wasm build.
- All state is in `struct Mars` (an `m42_ctx` of `lib/42mars.h`); every function takes `Mars *const m`. The wasm build and the native profiling tools compile with `-DM42_FIXED_CONTEXT`: one context `theMars`, and the core and the two static queues are separate static arrays reached through `CORE(m)` and `QUEUES(m)` (inside the struct, t20 was 1.4% slower: clang ordered the loop's loads and stores differently, #53). Without it (the native library) the context is in caller memory, 1 to 3% slower natively. Three things keep the wasm loops byte-identical, data addresses included (#55; check with an `llvm-objdump -d` diff of the three largest functions): `api.c` turns every handle into `CTX` with `M42_FIXED_CONTEXT` (a handle, or even `m ? CTX : 0`, stops clang from propagating the constant address into the loops); the arrays have `used` and an initializer (clang emits a static array where the first function uses it, so the queues-before-core layout depended on which export came first); new fields of `Mars` go to its end. New state goes into the struct, not into a static.
- The module exports the functions of `lib/42mars.h` and nothing else (`EXPORT()` in `api.c`), plus `memory` and `__heap_base`. `wasm/42mars.js` calls only those and gives the library all its memory, also the context's heap: its `Memory` class keeps the heap for the life of the instance and hands out scratch memory per call above it. A struct the glue writes or reads (`m42_rules`, `m42_match_options`, `m42_state`, `m42_warrior_state`, `m42_instruction`) has its wasm32 offsets in the glue's comments; `api.c` checks them with `_Static_assert`. Change both together.
- `asm.c` (the assembler) links after `mars.c` into the same module. The build has no libc and no compiler-rt: clang turned a string-length loop into a call to `strlen` and a 64-bit overflow multiply (also written as a division check, or as 32-bit halves) into `__multi3`, both undefined at link time (`no_builtin`, an empty `asm` barrier fix it, see `umulh()`). The C stack is 64 KB and lies below the data (an overflow traps, it does not corrupt), so recursion needs a limit; an exception inside wasm leaves the C stack pointer behind, which is why the glue drops the assembler's instance after one (#54).
- New code that the hot loops do not call goes behind them in `mars.c`, statics included: a function or static in front moved call indices and data addresses and cost the bench 1.1% without running (fifth round). Check that `execute`, `execute2_8000` and `execute2_any` are byte-identical apart from call indices with `node tools/wasm-functions.mjs <old.wasm> <new.wasm>`. Defining a function behind the loops is not enough: clang emits a static function where it is first referenced, and an existing function that grows can stop being inlined and become one of its own; both moved the call index of `warrior_died()` (#41). A small helper that is `M42_FORCE_INLINE` and called from functions that already exist adds none. `theMars` is 64-byte aligned, so that read-only data in front of it (a struct constant 32 bytes shorter, #41) moves the loops' field addresses only when it crosses a multiple of 64.
- Time an idea with a clean build: a build with statistics counters looked 1.3% and 2.9% faster natively than the same code without them (fifth round).
- A speed change is kept only with numbers from the `perf-experiment` skill and an entry in `docs/performance-log.md`. Smaller, simpler code wins ties.
- Where the time goes, t20, per simulated instruction: wasm 61.3 x86 instructions, 14.9 cycles (63.7 and 15.6 before the fourth round, of them about 5.8 stack-slot loads and stores and 1 stack check in `execute2_8000()`, #20; not counted again since); native 45.2 instructions, 12.2 cycles. L1 data misses: about 0.15 per simulated instruction, 80 to 90% in the core, nearly all L2 hits; memory stalls are at most 12% of the slots, and a prefetch, split value/word arrays and a 6-byte cell did not pay natively (issue #6). Open lead: Liftoff time before V8 tiers up on short runs. The spills are measured (log, "What V8 does with the two-warrior loop"): most changes that reduce live values in the C code moved V8's allocation the wrong way; one head for both queues (fourth round) is the exception, and two small follow-ups to it lost the whole gain again. Removing the stack check would give about 1%. The native build does not follow the wasm build: the fourth round is 4 to 7% faster in wasm and 2 to 3% slower natively with `clang -O3 -march=native`. Failed store-to-load forwards: the counter `ls_bad_status2.stli_other` also counts loads that were forwarded, and the only site worth a change was `ADD.F`/`SUB.F` (log, fourth round). Tie rounds are 36% (t20) and 47% (t80) of executed instructions; the exact tie proofs considered so far (state repetition, non-interaction) do not pay, and the closed-loop proof of #35 was built and saves 0.7% of t80 for a traced loop that costs more in V8, see the log (fifth round).
