# The pull request loop

The `gh` calls that take a change from a branch to a merged pull request and
back onto `main`, in order. Repository: `martinus/42mars`.

1. **Branch and commit**: one branch per PR from `origin/main` (`git fetch origin main && git switch -c issue-<n>-<slug> origin/main`). Never base a PR on another PR's branch and never merge `main` into a PR branch: GitHub's rebase merge refuses a merge commit, a stacked PR keeps the commits its base got rebased away, and both PRs had to be made again from new branches (#103 as #106, #108 as #109). A PR that needs another one waits for its merge, then branches from `origin/main`. Commit message `area: what changed`, then why and the numbers (see `git log`); no Claude attribution.
2. **Push and create**: before the first push, compare the test count of `npm test` with `docs/plan.md` and `README.md`. After a push, fix things in a new commit: the session may not force-push. `git push -u origin <branch>`, then `gh pr create --base main --head <branch> --title ... --body-file <file>`. Write the body to a file in the scratchpad first: the clean-room hook reads command text, and a body that names a blocked path or branch gets the command refused. Write it and run `gh pr create` in separate calls: in one batch a failed Write left the previous PR's body in the file, and #113 went up with "Fixes #92". The body lists the checks you ran with their results (pMARS checks, numbers before and after).
3. **Closing keywords only for what the PR finishes.** GitHub closes an issue for `Fixes #N`, `Closes #N` or `Resolves #N` anywhere in the PR body or a commit message, also inside quotes or tables and in prose ("a last PR that closes #88" closed #88 with #106). After `gh pr create`, `gh pr view <n> --json closingIssuesReferences --jq '[.closingIssuesReferences[].number]'` must list exactly the issues the PR finishes. A PR that does part of an issue names it by number only ("part of #N") and the issue body is updated to what is left (`gh issue edit N --body-file ...`).
4. **Watch CI**: `until gh pr checks <n> 2>/dev/null | grep -q .; do sleep 5; done; gh pr checks <n> --watch --interval 20` (right after `gh pr create` it prints "no checks reported" for a few seconds; after a push to an existing PR it still shows the last run until the new one starts, so wait for `grep -q pending` there; a plain `sleep` before it is refused by the harness). About 4 minutes, the fuzz job (3 targets of 60 s) is the slowest. For a failure: `gh run view <run-id> --log-failed`.
5. **Merge on green**: `gh pr merge <n> --rebase --match-head-commit $(git rev-parse HEAD)`. If the head moved, read the checks again on the new head; never force.
6. **Check what it closed**: `gh issue list --state open --author martinus`. GitHub closes the issues of a PR's `Fixes` lines one after the other, a few seconds apart (#78: #76 closed after #75); check again before closing by hand. Close each issue the PR finished that is still open: `gh issue close N --reason completed --comment "<what landed, numbers>"`. A speed idea that was measured and rejected is closed with `--reason "not planned"` and the numbers, after its log entry is merged.
7. **Back onto main**: `git fetch origin main && git switch -c <next-branch> origin/main`. Leave the merged branch alone; `gra done` cleans up worktrees, and only Martin runs it.
8. **Read the issue list again** (step 1 of the skill).
