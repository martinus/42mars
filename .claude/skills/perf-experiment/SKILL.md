# Speed experiment

Setup: `O=${COREWAR_ORACLE:-$HOME/.local/share/corewar-theater}`.

1. Read `docs/performance-log.md` first. Skip ideas already rejected there unless something they depended on changed; say what changed.
2. Idle machine: `uptime` load below 1 and `pgrep -a 'node|clang|pmars|chrome'` empty apart from yourself. Do not time while builds, tests or other agents run; ask first if another session may be benchmarking.
3. A/B in the same session: keep the baseline build (e.g. `cp src/engine/wasm/mars.wasm $TMP/base.wasm`), build the variant, and alternate baseline and variant runs (ABAB...), swapping `mars.wasm`, so drift hits both. Fresh process per run. `node tools/ab-wasm.mjs $TMP/base.wasm $TMP/variant.wasm` does that for bench, pairs, t20 and t80 and prints median, range and change; it restores `mars.wasm` afterwards. A change to a tool (e.g. `tools/tournament.mjs`) instead: `git show HEAD:tools/tournament.mjs > tools/zz-base-tournament.mjs` (its imports are relative), then `node tools/ab-tool.mjs tools/zz-base-tournament.mjs tools/tournament.mjs 5 <arguments>` alternates the two; delete the copy afterwards. For a change to `mars.c` that adds code outside the hot loops, run `node tools/wasm-functions.mjs $TMP/base.wasm src/engine/wasm/mars.wasm` first: when `execute`, `execute2_8000` and `execute2_any` (the three largest functions) differ in more than a call index, move the new code and its statics behind them before timing anything.
4. Measures (report median and range):
   | Name | Command | Runs |
   |---|---|---|
   | bench | `node tools/bench.mjs $O/corpus --wasm-match` (short, includes V8 warm-up) | 7 |
   | pairs | `node tools/bench-pairs.mjs $O/corpus` (40 random corpus pairs, broader instruction mix; `--early-tie`) | 7 |
   | native | `node tools/bench-native.mjs $O/corpus --runs 7`; two versions of `mars.c` alternately: `node tools/ab-native.mjs <A/mars.c> <B/mars.c> --input t20.in --early-tie` | 1 |
   | t20 | `node tools/tournament.mjs $O/sets/t20 --rounds 100 --seed 1 --jobs 1 --engine wasm` (time on stderr: `engine (wasm): N s`) | 7 |
   | t80 | same with `$O/sets/t80`, `--jobs 16` and `--jobs 31` | 5 each |
   | fixed cost | t80 with `--rounds 1 --jobs 31` (worker start, assembly, compile) | 5 |
   | JS | `node tools/bench.mjs $O/corpus --headless` (only for mars.js changes) | 7 |
   References, when re-measuring the summary: `node $O/cwbench/benchpairs.mjs` (bench pairs warmed up, ours vs corewar.dev exMARS: the fair single-thread comparison), `node $O/cwbench/split.mjs` (t20 split into pairings with and without tie rounds), `node $O/cwbench/single.mjs exmars` (short run like `tools/bench.mjs`, includes warm-up), `node $O/cwbench/tournament.mjs 31 $O/sets/t80.json`, `node tools/tournament.mjs $O/sets/t80 --rounds 100 --seed 1 --jobs 31 --pmars $O/bin/pmars` (native pMARS), and `node $O/cwbench/perpair.mjs $O/sets/t20.json` from the repo root to find pairings where we lose to exMARS.
   Tournament workloads for a change to scheduling or start-up, all with `--engine wasm --seed 1`: t80 with 16 and 32 jobs, t20 with 1 and 32 jobs, `$O/corpus --bench $O/corpus/agony.red --rounds 200` with 16 and 32 jobs (565 pairings), t80 with `--rounds 1`, and one pairing with `--rounds 1000`. The output tables must be byte-identical (`md5sum` of stdout) for every job count.
5. Keep only if t20 and bench are faster beyond noise (ranges do not overlap or a clear median shift over 7+7 runs), nothing else gets slower by more than 1%, and the `engine-check` skill passes. Otherwise restore the code and rebuild.
6. Record, also when rejected: one row in the right table of `docs/performance-log.md`: `| idea and why it should help | measure before → after | kept / rejected (reason) |`. For a kept change update the "State" line, and the speed numbers in `PLAN.md` (section Speed) and `README.md`.
7. For a profile, run the native build: `node tools/bench-native.mjs <dir or --input file> --keep <dir>` leaves the binary (`clang -O3 -march=native` on `bench-native.c`, which includes `mars.c`) and its `input.txt` in `<dir>`; then e.g. `perf stat -e instructions,cycles,L1-dcache-loads,L1-dcache-load-misses,branch-misses <dir>/bench <dir>/input.txt early-tie` or `perf record`. The tournament mix: `node tools/tournament.mjs $O/sets/t20 --rounds 100 --seed 1 --native-input t20.in`, then `--input t20.in --early-tie` (instruction count equals the wasm tournament's); corpus pairs: `tools/bench-pairs.mjs ... --native-input`. `--count <file>` writes executions per instruction word. Data addresses of loads (e.g. which L1 misses hit the core): `perf mem` finds no event on this machine, use AMD IBS: `perf record -e ibs_op/cnt_ctl=1/ -c 20011 -d <dir>/bench <dir>/input.txt early-tie`, then `perf script -F addr,data_src` and match the addresses against `nm -S <dir>/bench` (`coreMem`, `queueMem`, `arena`). The log has the last profiles.
