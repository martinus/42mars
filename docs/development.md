# Working on 42mars

How the repository is laid out, how to build and test it, how to compare it with pMARS and how to measure its speed. What the engine does is in [`redcode-semantics.md`](redcode-semantics.md), where the project stands in [`plan.md`](plan.md).

## Layout

| Folder | What is in it |
|---|---|
| [`lib/`](../lib) | The C library and nothing else. [`42mars.h`](../lib/42mars.h) is the public interface, [`42mars.c`](../lib/42mars.c) the one file to compile, which includes `src/`: [`mars.c`](../lib/src/mars.c) the simulator, [`asm.c`](../lib/src/asm.c) the assembler and expression evaluator, [`api.c`](../lib/src/api.c) the functions of the header, [`platform.h`](../lib/src/platform.h) everything that differs between gcc, clang and MSVC. [`42mars.def`](../lib/42mars.def) lists the exports of the Windows DLL. [`dispatch.h`](../lib/src/dispatch.h) is generated by [`gen-dispatch.mjs`](../lib/src/gen-dispatch.mjs). |
| [`cli/`](../cli) | `42mars`, the command line program with pMARS's options, on the public header only. |
| [`examples/`](../examples) | [`example.c`](../examples/example.c): a complete program on the library. |
| [`wasm/`](../wasm) | The npm package: [`42mars.wasm`](../wasm/42mars.wasm) (committed), [`42mars.js`](../wasm/42mars.js), the JavaScript interface over the functions of the header, and the types in [`42mars.d.ts`](../wasm/42mars.d.ts). [`build.sh`](../wasm/build.sh) builds the module. |
| [`ui/`](../ui) | Core War Theater, the visualizer. Plain ES modules, no build step. |
| [`tools/`](../tools) | Node programs on the npm package: `asm` (pMARS-style listing), `corpus` (assemble a folder), `tournament` (round robin on all cores), `serve`, and the comparisons with pMARS: `pmars-diff`, `expr-fuzz`, `example-check`. [`opcodes.js`](../tools/opcodes.js) has the opcode tables and the listing format, which `ui/` and the tests use too. |
| [`bench/`](../bench) | Everything that measures speed: `bench`, `bench-pairs`, `bench-native` (the C code built natively), `tie-ceiling`, `wasm-functions`, and `ab-wasm`, `ab-native`, `ab-tool` for alternating A/B timing. |
| [`test/`](../test) | `npm test`: [node:test](https://nodejs.org/api/test.html) files, the C test program in `test/c/`, the fuzz targets in `test/fuzz/` (`make fuzz`), results recorded from pMARS and from the removed JavaScript engines in `test/fixtures/`. |
| [`docs/`](.) | The semantics, the plan, the [performance log](performance-log.md) with every speed experiment, this guide, the README chart ([`images/speed.mjs`](images/speed.mjs)) and the logo ([`images/logo.svg`](images/logo.svg)). |
| [`warriors/`](../warriors) | Sample warriors written for this repository, and Dewdney's Imp and Dwarf. In [`warriors/koenigstuhl/`](../warriors/koenigstuhl): 5,261 warriors of the Koenigstuhl hills, downloaded 12th November 2026, without a license: test material, see its README. |

No dependencies: Node 20 or newer for the tests and tools, a C11 compiler for the library, clang 22 with the wasm32 target for the WebAssembly module.

## Build and test

```sh
npm test                    # all tests, about 9 s, on the committed 42mars.wasm
make                        # build/: lib42mars.a, the shared library, 42mars
make test                   # the C tests on these builds
wasm/build.sh               # after every change in lib/: rebuilds dispatch.h and 42mars.wasm
npm run serve               # the visualizer on http://127.0.0.1:8000/
```

`wasm/build.sh` is reproducible: two builds give the same bytes, and CI fails when the committed `42mars.wasm` or `dispatch.h` is not what it builds (Ubuntu's clang 22). So commit `42mars.wasm` together with the C change it came from.

On Windows, `build-msvc.bat` builds the same as `make` into `build\`, the static library and the DLL from one object (the DLL's exports are in `lib/42mars.def`, a test checks them against the header), then `set M42_BIN=build` and `node --test test/c-api.test.js test/cli.test.js`. MSVC compiles only the first 16 of the 32 specialized cases of `dispatch.h` (`M42_DISPATCH_16`), with all 32 `cl /O2` took 2 minutes. To check the plain C11 code that MSVC sees, on Linux:

```sh
make clean && make CFLAGS='-O2 -std=c11 -pedantic -Werror -DM42_PORTABLE' test
```

### Fuzzing

Three [libFuzzer](https://llvm.org/docs/LibFuzzer.html) targets in `test/fuzz/` run the C library on arbitrary input under ASan and UBSan: `fuzz_asm` (bytes as Redcode through every function of `42mars.h`, a match and stepping with a watch), `fuzz_eval` (bytes as an expression) and `fuzz_make` (warriors from `m42_warrior_make()` with raw or in-range fields and fuzzed rules; it traps when a warrior that does not fit the rules is played). They need clang.

```sh
make fuzz                                  # each target 60 s on 1 process
make fuzz FUZZ_SECONDS=1800 FUZZ_JOBS=8    # longer: 30 minutes each on 8 processes
make build/fuzz/fuzz_asm && build/fuzz/fuzz_asm build/fuzz/fuzz_asm-crash-<hash>   # run one input again
```

`make fuzz` fails on any sanitizer report, an input that takes more than 10 s or a process above 2 GB. The input is written to `build/fuzz/<target>-crash-*` (or `-timeout-*`, `-oom-*`), the log of each process to `build/fuzz/<target>-<n>.log`; in CI the job uploads both as the artifact `fuzz-failures`. Run the binary on the file to get the report again, under a debugger if needed. The corpus grows in `build/fuzz/corpus-<target>` and makes later runs start further. An input that found a defect also becomes a regression test in `npm test`, through `assemble` or `test/c/api-test.c`, so the fuzz job is not the only place that holds it.

CI ([`test.yml`](../.github/workflows/test.yml)) runs `npm test` on Node 20 to 26, checks the wasm build, builds and tests the library on Linux (x64, arm64), macOS and Windows and under ASan and UBSan, runs the fuzz targets for 60 s each, and makes the release archives. Its `pmars` job builds pMARS 0.9.5 from its archive (output hidden, see [the clean room](../README.md#written-in-a-clean-room-so-it-can-be-mit)) and compares scores, listings and `42mars` outputs with `tools/pmars-diff.mjs`, the t20 tournament and `tools/example-check.mjs`; it runs once the repository variables named at the top of the job are set. The per-round instruction counts and core hashes (`--pmars-trace`) and `tools/expr-fuzz.mjs` need patched pMARS builds and stay local checks. The Windows job reuses the MSVC object of `lib/42mars.c` from an earlier run while `lib/`, `build-msvc.bat` and the runner image stay the same (about 40 s less); a tag always compiles. A tag `v<version>` makes a GitHub release and publishes the npm package. The version is in `lib/42mars.h` and `package.json`, and a test checks that both agree.

## Compare with pMARS

pMARS 0.9.5 is the reference: same scores, same instruction count and same final core in every round. The comparison tools run a pMARS binary as a program; it needs the build options `-DSERVER -DEXT94 -DPERMUTATE -DRWLIMIT`. If you change engine code here, never read pMARS's source, see [the clean room](../README.md#written-in-a-clean-room-so-it-can-be-mit).

```sh
node tools/pmars-diff.mjs --pmars path/to/pmars --corpus path/to/warriors   # listings, expressions, sources, battles
node tools/tournament.mjs path/to/warriors --rounds 100 --pmars path/to/pmars --compare
node tools/example-check.mjs path/to/warriors --pmars path/to/pmars        # examples/example.c, the C library
make && node tools/pmars-diff.mjs --pmars path/to/pmars --corpus path/to/warriors --cli build/42mars --only cli
```

The warrior corpus used for all numbers in these docs is [n1LS/redcode-warriors](https://github.com/n1LS/redcode-warriors). Where pMARS has no defined result (lines over 255 characters, uninitialized memory on some operators, ...) 42mars does something reasonable instead and its assembler warns with a text that starts with `pMARS`; [`redcode-semantics.md`](redcode-semantics.md), section 4, lists these.

## Measure speed

Never compare a timing with a number from another day: the same `42mars.wasm` ran the same benchmark 16% faster in one session than in the next. Measure both sides, alternating, on an idle machine. The `bench/ab-*.mjs` scripts do that.

```sh
node bench/bench.mjs path/to/warriors --wasm-match         # 3 hill pairs, single thread
node bench/bench-native.mjs path/to/warriors --runs 7      # the same C code natively
node bench/ab-wasm.mjs base.wasm wasm/42mars.wasm          # two builds, alternating
node bench/wasm-functions.mjs base.wasm wasm/42mars.wasm   # which functions of the module changed
node docs/images/speed.mjs                                 # redraw the README chart from its numbers
```

[`performance-log.md`](performance-log.md) has every idea that was tried, with the numbers, also the ones that did not help. Commands in its entries before 12th November 2026 use the old paths: the speed tools were in `tools/` then and are in `bench/` now, `gen-dispatch.mjs` is in `lib/src/`.

## Conventions

- New source files start with `// SPDX-License-Identifier: MIT` and `// Copyright (c) 2026 Martin Leitner-Ankerl`.
- C is C11. Compiler specifics go into `lib/src/platform.h` only.
- No npm dependencies, no bundler. Browser code is plain ES modules.
- A behavior change of assembler or simulator goes into [`redcode-semantics.md`](redcode-semantics.md) in the same commit.
- Every bug fix gets a test that fails without the fix.
